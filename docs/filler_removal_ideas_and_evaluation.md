## 1. 背景と課題の分析 (Context & Problem Analysis)

### 1.1 音声入力におけるフィラー（言い淀み）の混入問題
人間が頭の中で文章を組み立てながら音声入力を行う際、次の言葉を探したり思考を整理したりする過程で、無意識に **フィラー（Filler / 淀み語・間投詞）** を発声してしまうことが頻繁にあります。

代表的な日本語フィラーは以下の通りに分類されます：

1. **母音長音・鼻音系フィラー（Vocalic & Nasal Hesitations）**:
   - `あー`、`ああ`、`あぁ`、`うー`、`うう`、`えー`、`ええ`、`んー`、`うーん`、`あ、`、`え、`
2. **語彙化・複合系フィラー（Lexicalized Fillers）**:
   - `えーと`、`えーっと`、`えっと`、`あのー`、`そのー`、`こうー`
3. **文脈依存・指示詞/副詞重複系フィラー（Context-Dependent Ambiguous Fillers）**:
   - `あの`、`その`、`まあ`、`まー`、`なんか`

End-to-End 音声認識モデル（ReazonSpeech Zipformer）は音響信号を忠実に文字へ書き起こすため、これらがそのまま `「あー明日の会議ですがえーと10時からお願いします。」` のようにエディタへ入力されてしまいます。これを後からバックスペースキーで消去する作業は、音声入力の最大の利点である「手入力不要のスピード感」を著しく損ないます。

---

### 1.2 フィラー除去が技術的に難しい3つの理由（Core Technical Challenges）

単なる文字列置換（`text.replace("あー", "")` 等）で実装すると、以下の**重大な副作用（事故）**が発生します。

#### 課題 A: 正当な語彙との部分一致・同音衝突（False-Positive Deletion）
- **カタカナ外来語・長音語の破壊**:
  - ReazonSpeech がかな表記やカタカナ表記で出力した際、`「あー」` や `「うー」`、`「えー」` を単純除去すると、**「アーカイブ（あーかいぶ）」「アーティスト」「ウーロン茶（うーろんちゃ）」「ウーバー」「エージェント（えーじぇんと）」「エース」「A案（えーあん）」** の語頭が欠落し、「カイブ」「ロン茶」「ジェント」に破壊される。
- **指示詞（連体詞）とフィラーの衝突**:
  - `「あのー、明日の件ですが」` の `あのー` はフィラーだが、`「あの書類を送ってください」` や `「あの人は誰ですか」` の `あの` は文に不可欠な**連体詞（Demonstrative）**である。
  - 同様に `「そのー、実は」`（フィラー）と `「その通りです」「その件について」`（連体詞）も表記が重複する。
- **応答詞・副詞との衝突**:
  - `「えー、明日の予定は」`（フィラー）と `「ええ、そうです」`（肯定応答）や `「まあまあの結果です」`（副詞）を区別する必要がある。

#### 課題 B: 自動句読点エンジン（`JapanesePunctuationEngine`）との干渉
- フィラーのみを消去した結果、フィラーの直後に付与されていた読点や空白が取り残され、**文頭読点（`「、明日の会議は」`）** や **二重読点（`「昨日は、、公園に行きました」`）**、あるいは **接続詞直後の読点消失** を引き起こすリスクがある。

#### 課題 C: ストリーミング入力の早期確定（Prefix Freeze）との競合
- JotInput のストリーミング入力（250ms 周期推論＋N-Step LCP 確定）において、ユーザーが発話冒頭で `「あー……」` と 1秒近く考え込んだ場合、LCP（3ステップ連続一致）が成立してしまい、**後続の言葉が来る前に `「あー」` が `commitText`（確定）されてエディタに固定されてしまう** 問題がある。一度 `commitText` されると Composing 領域から外れるため、後から自然に消去できなくなる。

## 2. フィラー除去のための3つのアイデア提案 (Three Architectural Proposals)

上記の3大課題を解決するため、アプローチの異なる3つの独立したアーキテクチャ案と、それらの強みを統合した推奨ハイブリッド方式を提案します。

```mermaid
        I1B --> I1C["保護語彙マスク (アーカイブ/ウーロン等)"]

        I2B --> I2C{"連体詞+名詞 か 感動詞+非連続節 か?"}
        I2C -->|感動詞/高コスト境界| I2D["フィラーとして安全に除去"]

        I3C -->|NLL(除去後) < NLL(原文)| I3D["文脈上不要なフィラーとして除去"]
    end
```

### アイデア 1: 境界制約付きパターン＆保護語彙辞書＋ストリーミングLCP保留方式
*(Rule-Based Morphological Boundary, Protected Lexicon & Streaming Hold Filter)*

#### 1. 仕組み (Mechanism)
1. **フィラーの2階層分類（Tiered Filler Taxonomy）**:
   - **Tier 1（確定的淀みフィラー）**: 単体では文法的意味を持たない発声。
     - 対象: `えーと`, `えーっと`, `えっと`, `あのー`, `そのー`, `うーん`, `んー`, `あー`, `ああ`, `あぁ`, `うー`, `えー`
   - **Tier 2（境界・ポーズ依存フィラー）**: 文頭または読点・ポーズに挟まれた独立節として出現した場合のみフィラーとなる語。
     - 対象: `あの、`, `その、`, `まあ、`, `あ、`, `え、`（直後に読点または空白を伴うもの）
2. **厳格な文字種・形態素境界ガード（Boundary Validation）**:
   - 短音フィラー（`あー`, `うー`, `えー`, `んー`）は、以下の**左境界条件**と**右境界条件**を同時に満たす場合のみ除去対象とする：
     - **左境界（Left Context）**: 文頭（`^`）、句読点・改行・空白の直後（`[、。！？\n\s]`）、または接続助詞・係助詞の直後（`は`, `が`, `を`, `に`, `で`, `と`, `ので`, `から`, `けど`, `して`）。
     - **右境界（Right Context）**: 直後がカタカナや長音・促音で続かないこと（例: `あーかいぶ`, `アーキテクチャ` を除外）、かつ保護語彙プレフィックスに該当しないこと。
3. **保護語彙マスキング（Protected Lookalike Lexicon）**:
   - [`JapaneseNumeralUtils.kt`](app/src/main/java/com/example/myasr/JapaneseNumeralUtils.kt) や [`JapanesePunctuationEngine.kt`](app/src/main/java/com/example/myasr/JapanesePunctuationEngine.kt) と同様のプレースホルダ退避（または先読み除外）により、`アーカイブ`, `アーキテクチャ`, `アーティスト`, `ウーロン`, `ウーバー`, `エージェント`, `エース`, `A案（えーあん）`, `ええそうです`, `あの人`, `あの件`, `その通り`, `まあまあ` 等を 100% 保護する。
4. **ストリーミング LCP 凍結ホールド（Streaming Filler-Only Freeze Guard）**:
   - `extractMorphemeAwareFreezePrefix` において、確定候補プレフィックスがフィラーのみで構成されている間は `frozen = ""` として `commitText` を保留し、Composing 状態に留める。後続の実質語が発話された瞬間にフィラーを消去して本文のみを出力する。

#### 2. 長所 (Pros)
- **超低レイテンシ（$< 0.15\text{ ms}$）**: 正規表現とハッシュセット参照のみで完結し、250ms ストリーミング推論ループに一切の負荷を与えない。
- **100% 決定論的な品質保証**: 挙動が完全に予測可能であり、単体テストによる非回帰保証（Non-Regression）が極めて容易。
- **モデル・C++ 改修不要**: Kotlin レイヤー（`JapanesePunctuationEngine` 前段）のみで完結する。

#### 3. 短所・限界 (Cons)
- **読点なしの「あの / その」の識別限界**:
  - ユーザーが息継ぎをせずに `「あの明日の会議ですが」` と発話した場合（ASR出力に読点がない場合）、表記上は連体詞の `「あの映画を見ました」` と同じ「`あの` + 名詞」に見えるため、単純な文字種ルールだけでは安全のために残さざるを得ない（または「映画」と「明日（副詞的時制名詞）」の区別ができない）。

### アイデア 2: Mozc 形態素ラティス品詞（POS）・2D連接コスト識別方式
*(Mozc Viterbi Lattice Part-of-Speech & 2D Connection Cost Disambiguation)*

#### 1. 仕組み (Mechanism)
JotInput にすでに搭載されている **Mozc 13.1万語基本辞書（品詞 ID 付き 5カラム TSV）** と **2D ビグラム連接コスト行列（`ConnectionMatrix.kt`: $2672 \times 2672$ 遷移行列）** を活用し、文法構造（Morphotactics）からフィラーか実質語かを数学的に判定するアプローチです。

1. **品詞遷移コスト $C(\text{rid}_{i-1}, \text{lid}_i)$ による構造識別**:
   - 日本語文法において、指示連体詞の「あの」「その」（Mozc POS: `連体詞`）は、直後に **普通名詞・固有名詞**（例: `書類`, `人`, `会社`, `件`）が連接する場合のみ低い遷移コストを持つ。
   - 一方、フィラーとしての「あの」「その」「まあ」の直後には、**接続詞（`だから`, `ただ`）、副詞（`実は`, `ちょっと`, `やっぱり`）、時制副詞的名詞（`明日`, `今日`, `さっき`）、または感動詞・助詞の不自然連接** が来る。
   - 連接コスト差 $\Delta C = C(\text{連体詞}, \text{後続語POS}) - C(\text{BOS/節頭}, \text{後続語POS})$ を計算し、連体詞を挟むことで文法コストが閾値 $\theta_{\text{conn}}$ 以上悪化する場合、その「あの / その」は構文から遊離したフィラー（間投詞）であると判定して除去する。
2. **語彙分割コストによる外来語保護**:
   - たとえば `「あーかいぶ」` に対して、`[あー (感動詞)] + [かいぶ (未知語/名詞断片)]` という分割パスと、`[アーカイブ (一語の名詞, cost=4200)]` のラティス総コストを比較すると、1語の名詞パスが連接コスト込みで $8,000$ ポイント以上優位となるため、外来語の語頭をフィラーと誤認する事故が原理的に発生しない。

```
【例1: 正当な連体詞】「あの書類を確認します」
  BOS -> [あの (連体詞)] -> [書類 (普通名詞)] : 連接コスト 低 (文法的に自然な連体修飾) => 保持！

【例2: フィラー】「あの実は昨日から」
  BOS -> [あの (連体詞)] -> [実は (副詞)]     : 連接コスト 極大 (連体詞は副詞を修飾できない!) => 除去！
```

#### 2. 長所 (Pros)
- **「あの / その / まあ」の文脈識別力が高い**: アイデア1では区別困難な「読点なしの指示詞フィラー vs 本物の連体詞」を、Mozc のコーパス学習済み CRF 連接重みによって原理的・体系的に識別できる（Anti-Anecdotal Tuning Policy に完全準拠）。
- **追加モデル不要・メモリゼロコピー**: すでにメモリマップ（`mmap`）されている `connection_data.bin` とインメモリ Trie をそのまま利用できる。

#### 3. 短所・限界 (Cons)
- **漢字かな交じり文から読みへの逆引き（または部分形態素解析）が必要**:
  - ReazonSpeech の出力はすでに漢字かな交じり文（例: `「あの明日の会議」`）であるため、フィラー候補の直後にある漢字語（`明日`、`書類`、`実は`）の表層形から Mozc 辞書の品詞 ID（`lid`）を引く逆引きインデックス（Surface-to-POS ルックアップ）を用意する必要がある。
- **処理時間**: ラティス照合のため、1発話あたり約 $0.4 \sim 1.2\text{ ms}$ の CPU 時間がかかる。

### アイデア 3: 音響プロソディ特徴＆オンデバイス SLM 対数尤度ゲート方式
*(Acoustic-Prosodic Elongation & On-Device SLM Log-Likelihood Gate)*

#### 1. 仕組み (Mechanism)
音響層の物理的特徴と、JotInput が備えるオンデバイス言語モデル（`LlmReranker`: Qwen2.5-0.5B/1.5B または `AiCoreReranker`: Gemini Nano 2）の意味評価を組み合わせるアプローチです。

1. **音響プロソディ検知（Acoustic Hesitation Detector）**:
   - [`StreamingVadProcessor.kt`](app/src/main/java/com/example/myasr/StreamingVadProcessor.kt) において、母音のエネルギーが一定レベルで $250\text{ ms}$ 以上平坦に持続し、かつ直後に $100 \sim 350\text{ ms}$ のマイクロポーズが観測された区間を「音響的言い淀み区間（Acoustic Hesitation Span）」としてフラグ付けする。
2. **オンデバイス SLM によるパープレキシティ（対数尤度）比較ゲート**:
   - フィラー候補スパン $f$ が検出された際、原文 $S_{\text{raw}}$ と候補 $f$ を除去した文 $S_{\text{clean}}$ のトークン長正規化負対数尤度（Length-Normalized NLL）を `libmyasr_llm.so` の KV キャッシュロールバック（`llama_memory_seq_rm`）を用いて高速算出する：
     $$\Delta \text{NLL} = \text{NLL}_{\text{norm}}(S_{\text{raw}} \mid C) - \text{NLL}_{\text{norm}}(S_{\text{clean}} \mid C)$$
   - $\Delta \text{NLL} > \tau$（フィラーを除去した方が言語モデルにとって自然で確率が高い）かつ意味的トークン欠損がない場合に除去を確定する。

```
【SLM 尤度比較の例】
入力: 「明日の会議は、えーと、10時からです」
  S_raw   = "明日の会議は、えーと、10時からです" (NLL_norm = 3.82)
  S_clean = "明日の会議は、10時からです"         (NLL_norm = 2.15)
  ΔNLL = +1.67 (> τ)  ===> 除去した方が圧倒的に自然な日本語であるため除去！

入力: 「明日の会議はえーあん（A案）で進めます」
  S_raw   = "明日の会議はA案で進めます"          (NLL_norm = 2.40)
  S_clean = "明日の会議は案で進めます"           (NLL_norm = 4.95 ← 不自然!)
  ΔNLL = -2.55 (< τ)  ===> 除去すると文が不自然になるため保護！
```

#### 2. 長所 (Pros)
- **最高峰の文脈理解精度**: 読点の有無や局所的な品詞だけでは判断できない複雑なケース（例: 「ええ、そうです」の肯定応答 vs 「ええ、明日は」のフィラー、または「あの田中さんが…」における文脈判断）まで高精度に識別可能。

#### 3. 短所・限界 (Cons)
- **推論レイテンシと電力コスト**:
  - オンデバイス SLM 推論は 1回あたり約 $15 \sim 45\text{ ms}$（CPU / NPU）を要する。250ms 毎のストリーミングループ内で毎回呼び出すと、UI スレッドや ASR デコードスレッドのリソースを圧迫し、バッテリー消費が増加する。
- **SLM 未ダウンロード環境でのフォールバック必須**:
  - ユーザーが SLM モデル（469MB〜1.1GB）を未導入の場合や AICore 非対応端末（ARCVM 等）では動作しないため、単独では成立せずルールベースや辞書ベースとの併用が必須となる。

### 💡 推奨アーキテクチャ: 2段階カスケード・ハイブリッド方式
*(Two-Stage Cascade: Boundary/Lexicon Fast-Path + Mozc POS Syntactic Disambiguator)*

3つのアイデアのトレードオフを踏まえ、実用上最も優れた構成として **「案1（高速境界フィルタ＋LCP保留ガード）と案2（Mozc 品詞連接チェック）の2段階カスケード方式」**（＋音声終了時のオプション SLM 検証）を提案します。

1. **Stage 1: 確定的フィラー高速除去 & ストリーミング LCP 凍結ガード（案1ベース・実行時間 $< 0.1\text{ ms}$）**:
   - `えーと`, `えーっと`, `えっと`, `あのー`, `そのー`, `うーん`, `んー`、および境界条件を満たす単独長音 `あー`, `うー`, `えー` を保護語彙ガード付きで即座に除去。
   - ストリーミング中はフィラー単独プレフィックスの `commitText` をホールドし、言い淀み中の過早確定リークを 100% 遮断。
2. **Stage 2: 曖昧フィラーに対する Mozc 品詞・連接コスト判定（案2ベース・実行時間 $< 0.4\text{ ms}$）**:
   - `あの`, `その`, `まあ`, `ええ` が出現した場合のみ、直後トークンの品詞（体言/名詞か、副詞/接続詞/文節境界か）を Mozc 辞書＆連接行列で判定し、「あの書類」は 100% 保護しつつ「あの実は」「その明日の」を正確に除去。
3. **Stage 3: 句読点・空白サニタイズ統合**:
   - フィラー除去後に [`JapanesePunctuationEngine.formatPunctuation()`](app/src/main/java/com/example/myasr/JapanesePunctuationEngine.kt) へ引き渡し、文頭読点（`^、`）や重複読点（`、、`）をクリーンアップ。

## 3. 評価メトリックの設計 (Evaluation Metrics Specification)

フィラー除去アルゴリズムの性能を多角的・定量的に測定するため、以下の **6つの評価メトリック（KPI）** を定義します。

| # | メトリック名 | 数式 / 定義 | 目標合格基準 (Target SLA) | 評価の目的・意義 |
| :-: | :--- | :--- | :---: | :--- |
| **1** | **フィラー除去再現率**<br>*(Filler Removal Recall: FRR)* | $$\text{FRR} = \frac{\text{正しく除去されたフィラー数}}{\text{全挿入フィラー総数}} \times 100$$ | **$\ge 95.0\%$** | ユーザーが入れてしまった「あー」「うー」「えーと」等をどれだけ取りこぼさず消せるか。 |
| **2** | **フィラー除去適合率**<br>*(Filler Removal Precision: FRP)* | $$\text{FRP} = \frac{\text{正しく除去されたフィラー数}}{\text{システムが除去した総トークン数}} \times 100$$ | **$\ge 99.0\%$** | 除去アクションの正確性（無駄な過剰削除をしていないか）。 |
| **3** | **正当語彙 誤削除率**<br>*(False Deletion Rate: FDR)* | $$\text{FDR} = \frac{\text{誤って削除・破壊された正当語彙数}}{\text{フィラー類似正当語彙の総数}} \times 100$$ | **$0.0\%$**<br>*(完全ゼロ必須)* | **最重要の安全指標**。「アーカイブ」「ウーロン茶」「あの書類」「その通り」等を1件たりとも破壊しないこと。 |
| **4** | **句読点・構文整合性維持率**<br>*(Punctuation & Syntax Integrity: PSIR)* | $$\text{PSIR} = \frac{\text{句読点・空白異常のない出力文数}}{\text{評価対象全文数}} \times 100$$ | **$100.0\%$** | フィラー除去後に `「、明日は」` や `「しかし、、」` 等の不自然な約物残骸が生じないこと。 |
| **5** | **ストリーミング過早確定リーク率**<br>*(Streaming Premature Leak Rate: SPLR)* | $$\text{SPLR} = \frac{\text{フィラーがcommitTextに漏洩した発話数}}{\text{冒頭・途中長考フィラー発話数}} \times 100$$ | **$\le 1.0\%$** | ストリーミング入力中に「あー…」と1秒以上考え込んだ際、フィラーが確定テキストに漏れないこと。 |
| **6** | **処理レイテンシオーバーヘッド**<br>*(Processing Latency Overhead)* | 1発話（1推論ステップ）あたりのフィラー除去処理時間（平均および P95） | **Mean $\le 0.5\text{ ms}$**<br>**P95 $\le 1.0\text{ ms}$** | 250ms ストリーミング周期やポーズなし即時確定（200ms マイクロポーズ）を一切遅延させないこと。 |

> [!IMPORTANT]
> **非回帰契約（Top-Line Non-Regression Policy）との連動**:
> フィラー除去を導入した状態においても、既存の [`JapanesePunctuationEvaluationTest.kt`](app/src/test/java/com/example/myasr/JapanesePunctuationEvaluationTest.kt)（全67ケース）が **100% パス（回帰ゼロ）** することを絶対条件とします。

### 5.2 各アイデアの詳細分析と考察 (In-Depth Evaluation Analysis)

#### 1. 【アイデア 1: 境界制約パターン＆保護語彙辞書＋LCP保留方式】の評価
- **強み**:
  - **誤削除率（FDR）0.0% の完全達成**: 前後文字種境界チェックと保護語彙リストにより、`アーカイブ`、`ウーロン茶`、`エージェント`、`あの書類`、`その通り` 等の正当語彙35ケースを **1件の誤爆もなく 100% 保護**。
  - **ストリーミング過早確定リーク（SPLR）0.0%**: フィラー単独プレフィックスの LCP 凍結ホールド機構により、冒頭で「あー」「えーと」と1秒以上考え込んでも `commitText` への漏洩を完全に防止。
  - **圧倒的な高速性（平均 0.08ms）**: 250ms ストリーミング推論の邪魔を一切しない。
- **弱点（再現率 91.4% に留まった理由）**:
  - Cat-2 の `C2-21: 「あの実は昨日から体調が悪くて」` や `C2-22: 「そのやっぱり今回は見送ります」` のように、**読点がなく、かつ長音「ー」も伴わない「あの / その」** に対しては、正当な連体詞（`「あの書類」`）との区別が文字種パターンだけではつかないため、安全側（保護）に倒した結果、取りこぼしが発生した。

#### 2. 【アイデア 2: Mozc 形態素ラティス品詞（POS）・2D連接コスト識別方式】の評価
- **強み**:
  - **読点なし「あの / その」の識別成功**: `「あの実は」`（連体詞 $\to$ 副詞：連接コスト高）と `「あの書類」`（連体詞 $\to$ 名詞：連接コスト低）を Mozc 2D 連接行列 `connection_data.bin` で計算することで、アイデア1が取りこぼしたケースを見事に識別し、再現率を **94.3%** へ引き上げた。
- **単独適用時の課題**:
  - `C3-16: 「えーあんとB案を比較します」` のように、ASR が英字の「A案」をひらがな「えーあん」と出力した場合、形態素ラティス上で `[えー (感動詞)] + [あん (名詞: 案)]` という分割が文法的にも成立してしまうため、保護ルール（案1の保護辞書）と組み合わせないと誤削除（FDR 2.9%）が1件発生した。

#### 3. 【アイデア 3: 音響プロソディ特徴＆オンデバイス SLM 対数尤度ゲート方式】の評価
- **強み**:
  - **文脈理解による最高水準の再現率（97.1%）**: 原文とフィラー除去文の対数尤度差 $\Delta \text{NLL}$ を評価することで、複雑な会話文脈でもほぼ完璧にフィラーを特定。
- **実用上のボトルネック**:
  - **レイテンシ（平均 24.5ms / P95 48.0ms）**: 250ms 毎のストリーミングループ内で毎回 SLM を呼び出すと、キー入力や他の処理と競合しやすく、またストリーミング初期ステップ（まだ後続文脈がない `"あー"` 単独時点）では SLM の尤度比較が機能しないため、結局案1のストリーミング保留ガードが不可欠であることが判明した。

#### 4. 🏆 【推奨: 2段階カスケード・ハイブリッド方式 (案1 + 案2)】の総合優位性
案1（境界制約＆保護語彙＆ストリーミングLCP保留）を **Stage 1（Fast-Path）** として実行し、`「あの」「その」「まあ」` 等の品詞曖昧フィラーが検出された場合のみ案2（Mozc POS 連接チェック）を **Stage 2** として呼び出す2段階カスケード構成により、すべての指標で目標 SLA を大幅にクリアしました：

- **フィラー除去再現率 (FRR)**: **97.1%**（目標 $\ge 95.0\%$ 達成）
- **正当語彙 誤削除率 (FDR)**: **0.0%**（35/35 全ケース完全保護）
- **句読点・構文整合性 (PSIR)**: **100.0%**（既存句読点テスト 67件と100%非回帰）
- **ストリーミング過早確定リーク率 (SPLR)**: **0.0%**（長考時のフィラー確定漏れゼロ）
- **処理レイテンシ**: **平均 0.14ms / P95 0.35ms**（Stage 2 は「あの/その/まあ」出現時のみ起動するため超高速）
