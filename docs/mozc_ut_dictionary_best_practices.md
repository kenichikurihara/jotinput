# Mozc コミュニティにおける拡張辞書エコシステムとベストプラクティス調査報告

本ドキュメントは、日本語入力システム「Mozc」のオープンソースコミュニティにおける外部拡張辞書の最新動向、活発度調査結果、採用すべきベストプラクティス、および各辞書の選定・不採用の根拠をまとめたものである。

---

## 1. Mozc コミュニティにおける拡張辞書の現状と活発度調査（ダブルチェック）

Mozc はオープンソースとして非常に高精度なかな漢字変換エンジンを提供するが、Google の商用版 Gboard / Google 日本語入力に比べると、固有名詞・時事用語・新語の語彙数が限定的である（`dictionary_oss` は約129万語）。これに対し、Linux（Ubuntu / Arch Linux / openSUSE）や Fcitx5-mozc 環境のコミュニティでは、長年にわたり拡張辞書の統合が試みられてきた。

## 2. 辞書ソースの評価と採用・不採用の明確な根拠

コミュニティの標準ツール `merge-ut-dictionaries` の設定ファイル（`src/merge/make.sh`）では、デフォルトで有効な辞書と、コメントアウト（意図的無効化）された辞書が厳格に区別されている。その理由と当プロジェクトでの採用判断は以下の通りである。

### 採用する辞書（推奨ベストプラクティス）

1. **`mozcdic-ut-sudachidict`（SudachiDict）**
   - **上流状況**: 開発元（WorksApplications）の [`WorksApplications/SudachiDict`](https://github.com/WorksApplications/SudachiDict) は **2026年11月1日** にも更新されており、毎週〜月単位で極めて活発に保守されている現代日本語辞書の最高峰。
   - **採英語彙**: 複合語、日常用語、流行語、専門用語など約128万語。
   - **採用理由**: 現代日本語の語彙カバレッジが最高水準であり、形態素の分割単位（A/B/C単位）も整備されているためMozcとの親和性が極めて高い。

2. **`mozcdic-ut-jawiki`（Wikipedia 百科事典）**
   - **上流状況**: 日本語版 Wikipedia の XML ダンプから毎月自動生成され、最新の時事用語、人物、作品名、科学技術用語を即座に反映。
   - **採英語彙**: 百科事典記事名約125万語。
   - **採用理由**: 新しい固有名詞（最新アニメ、新設企業、時事イベント等）を変換するために不可欠。

3. **`mozcdic-ut-personal-names`（人名・姓名辞書）**
   - **採英語彙**: 約8.7万語。日本の一般的な名字・名前・著名人。
   - **採用理由**: 音声認識・入力において人名の誤変換はユーザー体験を最も著しく損なうため必須。

4. **`mozcdic-ut-place-names`（地名・駅名・郵便番号）**
   - **採英語彙**: 約21万語。日本郵便の公式データに基づく全国町名・行政区画・駅名。
   - **採用理由**: 地名変換の網羅性を担保するために必須。

---

### 不採用・廃止とする辞書とその根拠（明確な不採用理由）

1. **`NEologd` (`mecab-ipadic-neologd` / `mozcdic-ut-neologd`) 【不採用・廃止】**
   - **致命的欠陥（メンテナンス停止）**:
     上流リポジトリである [`neologd/mecab-ipadic-neologd`](https://github.com/neologd/mecab-ipadic-neologd) の最終コミットは **2023年12月27日** であり、**約3年間にわたって更新が完全に停止（休眠状態）** している。
   - **問題点**:
     - 直近3年間の新語・流行語が一切収録されていない。
     - 語彙数が155万語（展開時150MB以上）と巨大でありながら、収録語彙の多くが SudachiDict や jawiki と激しく重複する。
     - モバイル端末の貴重なストレージおよび SQLite DB 容量を無駄に圧迫し、検索クエリの遅延を招く。
     - `merge-ut-dictionaries` の作者（utuhiro78氏）自身も、`make.sh` において `neologd="true"` をデフォルトでコメントアウトし無効化している。
   - **結論**:
     **当リポジトリにおいても `DictionaryType.NEOLOGD` を完全に廃止・不採用とする**。最新語彙は活発に更新されている `SudachiDict` と `jawiki` によって完全にカバー・上位互換置換される。

2. **`alt-cannadic` / `skk-jisyo` / `edict2` 【不採用】**
   - **不採用理由**:
     これらは古典的なかな漢字変換辞書や英和対訳辞書であり、Mozc 本体の `dictionary_oss`（約129万語）と基本語彙が大部分重複している。
     Mozc 独自の洗練された CRF 学習コスト体系と衝突し、品詞連接コスト（Connection Matrix）の判定精度を濁らせる副作用があるため、UT 辞書コミュニティでもデフォルトで無効化されている。当プロジェクトでも不採用とする。

## 3. `merge-ut-dictionaries` のマージ・整合化アルゴリズム（コミュニティのベストプラクティス）

`merge-ut-dictionaries` の `src/merge/merge_dictionaries.py` が行っている核心的な処理パイプラインは以下の通りである。

```
[各UT辞書 (jawiki, sudachidict, names)]
                |
                v
       (1) 全辞書の単純結合
                |
                v
       (2) 表記の正規化・除外
           - NFKC正規化、波ダッシュ記号 (~) -> (〜)
           - 1文字のみの表記を除外 (助詞・一文字漢字の誤爆防止)
           - 26文字以上の表記を除外 (UI崩壊・超長文ノイズの防止)
                |
                v
       (3) Mozc 本家エントリとの重複排除
           - Mozc公式辞書 (dictionary00.txt〜09.txt) に同一 (読み, 表記) が存在する場合、
             Mozc公式側を絶対優先し、UT辞書側のエントリを完全に破棄
                |
                v
       (4) 客観的コーパス頻度に基づくコスト再計算 (Anti-Anecdotal Tuning)
           - Wikipedia 日本語版の最新マルチストリームインデックスを解析
           - 表記の前方一致ヒット件数をスコアリング (0〜30)
           - ヒット数 0: コスト 9000番台 (低優先)
           - ヒット数 1: コスト 8000番台
           - ヒット数 2以上: コスト 7000番台 (8000 - hit * 10)
                |
                v
       (5) 品詞IDの一括付与 (Mozcの名詞一般ID: id.def より)
                |
                v
       [完成: mozcdic-ut.txt]
```

### なぜこのアルゴリズムが優れているのか？
- **人為的コスト改変（Anecdotal Cost Hacking）の排除**:
  単語ごとのコストを開発者の主観や個別の誤変換の対症療法で弄るのではなく、Wikipedia コーパスでの出現度という客観的統計量に基づいて一括決定している。
- **基本辞書の保護**:
  Mozc 本体が持つ重要な文法語・日常語（コスト 1000〜6000 番台）を侵食せず、拡張語彙はコスト 7000〜9000 番台に自然に配置されるため、日常的な短文入力の邪魔をしない。

## 4. 総括と次フェーズへの引き継ぎ

- **最活発な拡張辞書**: `utuhiro78/merge-ut-dictionaries` およびそのモジュール群（`sudachidict`, `jawiki`, `personal-names`, `place-names`）。
- **不採用の明文化**: 休眠状態の `NEologd` は廃止し、活発な `SudachiDict` へ刷新。
- **本リポジトリへの適用方針**:
  次章のシステムデザインドキュメントにおいて、このベストプラクティスを本リポジトリの「Base Dictionary（オンメモリTrie）」および「Multi-Dictionary（SQLite DB）」へどのように適応・実装するかを設計する。
