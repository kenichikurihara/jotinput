# フリップ入力におけるフレーズ確定後「次フレーズ予測（つながり予測）」アイデア集・イテレーション・総合評価レポート

## 1. 概要と背景

### 1.1 課題と目的
JotInputのフリック入力（かなキーボード入力）において、現在ユーザーが特定のフレーズ（単語・文節・定型句）を確定（コミット）した直後は、候補表示バー（`CandidateStripView`）がプレースホルダー（「話すか、フリックで入力」）に戻り、空状態となります。

しかし、スマートフォンにおける自然な日本語入力では、フレーズを確定した直後（次のキーを打つ前 = **Zero-query / Next-phrase prediction**）に、次に続く可能性の高いフレーズやつながる単語が候補バーに先行提示されることで、ユーザーは次の文字をキーボードでタイピングすることなく、タップのみで文章をリズミカルに書き進めることができます（例: 「よろしく」確定 $\to$ 「お願いします」「お願いいたします」が即座に出現）。

本ドキュメントでは、確定後の次フレーズ予測サジェストを実現するための多様なアイデアを多角的・網羅的に発想・イテレーションし、モバイルIME特有の厳格な制約（超低遅延 $< 1\text{ ms}$、省メモリ、バッテリー効率、プライバシー、ANR防止）に照らし合わせて詳細に評価・選定します。

## 2. アイデア生成とイテレーションの記録

アイデア発想にあたり、単一の技術に偏らず、以下の多角的な視点からアプローチを洗い出し、段階的に深化・洗練（イテレーション）させました。

### 【視点 A: ユーザー統計・動的学習キャッシュ】
- **Idea 1: 確定バイグラム/N-gram 遷移頻度キャッシュ（User Bigram / N-gram History Cache）**
  - **概要**: ユーザーが過去に入力した「フレーズ $A$ の直後にフレーズ $B$ を確定した」という履歴ペア $(A \to B)$ を、カウントおよび最終利用日時（LRU）とともにローカルJSON / SQLiteに永続化保存。
  - **動作**: フレーズ $A$ が確定された瞬間、キー $A$ に紐づく後続候補 $B_1, B_2, \dots$ を頻度順に候補バーへ表示。
  - **深化イテレーション**:
    - 単純な頻度カウントだけだと昔の入力が固定化されるため、**時間減衰スコアリング（Half-life decay）またはLRUボーナス**を組み合わせる。
    - 単語単位だけでなく、文末（「。」）や記号（「！」）とのペアも記録し、文頭の書き出し予測にも対応させる。

### 【視点 B: 言語統計・辞書ベースの定型コロケーション】
- **Idea 2: 辞書内蔵の標準日本語コロケーション・定型連語テーブル（Canonical Collocation Dictionary）**
  - **概要**: 新規インストール時や履歴が存在しない語句（コールドスタート時）でも自然なサジェストが出るよう、一般的な日本語の頻出連語（ビジネス挨拶、接続詞、複合動詞等）を事前定義テーブルとして組み込む。
  - **例**:
    - 「よろしく」 $\to$ 「お願いします」「お願いいたします」「どうぞ」
    - 「ありがとう」 $\to$ 「ございます」「ございました」
    - 「お疲れ様」 $\to$ 「です」「でした」
    - 「ご検討」 $\to$ 「のほど」「よろしく」
    - 「確認」 $\to$ 「しました」「いたします」「お願いします」
  - **深化イテレーション**:
    - Mozcの品詞連接コスト（2-gram / 3-gram）から事前抽出し、軽量な静的バイグラムマップとしてアプリにバンドルすることで、辞書サイズを数十KBに抑えつつ自然な日本語表現を網羅する。

### 【視点 C: 日本語文法・助詞/補助動詞のスマート自動補完】
- **Idea 3: 文法規則ベースの後続品詞サジェスト（Grammatical Continuation / Particle Prediction）**
  - **概要**: 日本語の文法構造（膠着語）に着目し、確定された直前フレーズの品詞（体言、用言連用形など）に応じて次に必ず現れる助詞や補助動詞をサジェストする。
  - **例**:
    - **名詞（体言）確定後**: 格助詞・副助詞（「は」「が」「を」「に」「で」「の」「と」「も」「へ」）をサジェスト。
    - **動詞テ形・連用形確定後**: 補助動詞（「いる」「おる」「みる」「おく」「しまう」「ください」）をサジェスト。
    - **形容詞語幹確定後**: 「です」「でした」「そう」「ない」をサジェスト。
  - **深化イテレーション**:
    - フリック入力で助詞（特に「は」「が」「を」等）を入力するには1〜2回のフリック操作が必要だが、確定直後に候補バーの先頭に助詞が並んでいれば、1タップで助詞を確定でき、入力ストローク数が半減する。

### 【視点 D: オンデバイスSLM（小型言語モデル / llama.cpp）による生成】
- **Idea 4: オンデバイスSLM（Qwen2.5-0.5B）による Zero-Query 次フレーズ先読み生成**
  - **概要**: 現在の入力フィールド全体のカーソル前文脈（`textBeforeCursor`）をプロンプトとして、バックグラウンドで動作するオンデバイスSLM（`LlmReranker`）にオートリグレッシブ（自己回帰）なNext-Token / Next-Phrase生成を行わせ、次の文節を先読みサジェストする。
  - **例**: 「明日の会議の資料について、準備が」確定 $\to$ SLMが「整いました」「進んでおります」を生成して候補バーに表示。
  - **深化イテレーション**:
    - スマホCPUでのSLM生成は1トークンあたり 30〜80ms を要する。
    - 確定直後のユーザーの思考時間（約 200〜500ms）を利用して非同期コルーチンで生成すれば、体感待ち時間なしで高度な文脈適応候補を提示できる。
    - ただし、ユーザーが次のキーを押した瞬間に即座に `job.cancel()` で中断し、メインスレッドへの負荷やバッテリー浪費をゼロにする必要がある。

### 【視点 E: コンテキスト・メタデータ適応型サジェスト】
- **Idea 5: 状況・時間帯・アプリ環境ヒューリスティクス（Contextual & Temporal Heuristics）**
  - **概要**: 入力フィールドが空の状態、または句点（「。」）や改行の直後に、現在の時刻（朝/昼/夜）や入力先アプリ（メール/Slack/LINE/検索）に応じて適切な書き出し候補をサジェストする。
  - **例**:
    - 午前（8:00〜11:00）: 「おはようございます」「お疲れ様です」「お世話になっております」
    - 午後・夜: 「お疲れ様です」「お世話になっております」「こんばんは」
    - 句点「。」確定直後: 「また、」「つきましては、」「なお、」「そのため、」

### 【視点 F: クラウドLLM連携型サジェスト】
- **Idea 6: クラウドLLM API（Gemini API等）による次文・次フレーズ予測**
  - **概要**: 確定フレーズと前後の文脈を外部のクラウドLLMエンドポイントに送信し、極めて高度で長文にわたる次の文節・フレーズ予測を取得する。
  - **深化イテレーションでの課題検証**:
    - ネットワーク通信が発生しレイテンシが 200〜800ms かかる。
    - オフライン環境（地下鉄、飛行機、電波微弱エリア）で動作しない。
    - IMEで入力中のテキスト全体を外部サーバへ送信することは、重大なプライバシー上の懸念（機密情報・パスワード漏洩リスク）を招く。

### 【視点 G: 多層ハイブリッド予測パイプライン（Multi-Tier Hybrid Architecture）】
- **Idea 7: Fast-Path（履歴バイグラム＋静的定型句＋助詞）+ Async Slow-Path（SLM非同期生成）の2階層ハイブリッド**
  - **概要**: アイデア1〜5の強みを統合し、弱点を相互補完するアーキテクチャ。
    - **第1層 (Fast-Path, メインスレッド, $< 0.1\text{ ms}$)**:
      - 確定した瞬間に、ユーザー履歴バイグラムキャッシュ（Idea 1）と静的連語・助詞テーブル（Idea 2, 3）から即座に候補を抽出して `CandidateStripView` に描画。
      - 画面のフレームレート（60〜120fps）を完全に維持し、ユーザーにレイテンシを一切感じさせない。
    - **第2層 (Async Slow-Path, バックグラウンド, $50\sim 200\text{ ms}$)**:
      - SLMが準備完了かつ利用可能な場合、ユーザーがキー入力を行わないアイドル時間を利用して、長文コンテキストに基づく文脈予測（Idea 4）を生成し、候補バーに優雅に追加・マージする。
    - **入力割り込み契約（Instant Preemption）**:
      - ユーザーが次の文字を1キーでもフリックした瞬間、予測モードは直ちに解除され、即座に通常の「かな漢字変換パイプライン」へと切り替わる。

## 3. 全アイデアの評価マトリクス

8つの評価基準に基づいて各アイデアを比較評価します：
1. **応答レイテンシ（Latency）**: 確定後、候補が画面に現れるまでの時間（目標: $< 1\text{ ms}$）
2. **UIスレッド安全性（Safety）**: メインスレッドをブロッキングせず、DaveyスパイクやANRを引き起こさないか
3. **精度・文脈適合度（Quality）**: ユーザーの入力意図に合致した候補を出せるか
4. **メモリ/ストレージ負荷（Footprint）**: メモリ圧迫やアプリサイズ増大がないか
5. **バッテリー/CPU効率（Efficiency）**: バッテリー消費を浪費しないか
6. **オフライン/自律動作（Offline）**: ネットワーク接続なしで動作するか
7. **プライバシー安全性（Privacy）**: 機密データが外部に漏洩しないか
8. **実装実現性・堅牢性（Feasibility）**: 複雑になりすぎず、安定して保守可能か

## 4. 評価結果と採択アーキテクチャの決定

### 4.1 却下されたアプローチ
- **Idea 6 (クラウドLLM連携)** は却下とします。IME（ソフトウェアキーボード）はパスワードや個人情報、プライベートなチャットを直接扱うコンポーネントであり、入力内容をリアルタイムに外部クラウドへ送信することはプライバシーポリシー上およびセキュリティ上容認できません。また、オフライン動作ができない点もJotInputのコア哲学（完全オンデバイスASR/IME）に反します。

### 4.2 採択アーキテクチャ：2階層多層ハイブリッド予測（Tiered Hybrid Prediction Engine）
総合評価 **SS** となった **Idea 7 (多層ハイブリッド)** を本プロジェクトの設計として正式採択し、実装を完了しました。

具体的には、以下のレイヤーをシームレスに統合しています：

1. **Layer 1: ユーザー履歴バイグラム学習キャッシュ（User Bigram Cache）**
   - ユーザーがフレーズ $A$ を確定した直後にフレーズ $B$ を確定した際、ペア $(A \to B)$ を記録・カウントアップ。
   - アプリ終了後も次回起動時に引き継げるよう、ローカルJSON（`next_phrase_cache.json`）に非同期永続化。
   - ユーザー個人の入力傾向（例: 「了解」$\to$「です」、「よろしく」$\to$「お願いいたします」）を自動学習。

2. **Layer 2: 辞書内蔵の標準連語・コロケーション＆助詞テーブル（Canonical Collocations & Particles）**
   - 新規インストール直後や未学習の単語であっても、頻出する日本語表現（挨拶、依頼、相槌、ビジネス定型句）を瞬時に予測。
   - 名詞確定後には高頻度格助詞（「は」「が」「を」「に」「で」「の」「と」）をサジェストし、フリックストロークを劇的に削減。

3. **Layer 3: オンデバイスSLM（Qwen2.5-0.5B）による投機的先読み生成＆文脈リランキング（Slow-Path Worker）**
   - llama.cpp のネイティブC++エンジン（[`llm_reranker.cc`](file:///home/kenichikurihara/repos/myasr/app/src/main/cpp/llm_reranker.cc)）において `PredictNextPhrases` を実装。
   - 直前の入力文脈（`textBeforeCursor`）のロジットから、自然に続く上位トークンを探索し、最大数トークン先まで貪欲法で自動生成（例: 「準備が」$\to$「整いました」「できました」）。
   - 履歴バイグラムや定型句とマージした候補群をSLMの因果対数尤度（Causal Log-Likelihood）で文脈スコアリングし、最も文脈に即した順序で提示。

4. **Layer 4: ゼロレイテンシ Fast-Path + 即時プリエンプション契約**
   - フレーズ確定イベントのトリガーを受け、**メインスレッド上で $< 0.1\text{ ms}$** で Fast-Path 候補を即時表示。
   - ユーザーのアイドル時間（思考時間）中にバックグラウンドSLMワーカーが候補をさらに賢く更新。
   - ユーザーが次のフリック入力を開始した瞬間に、コルーチンは直ちにキャンセルされ、通常の未確定文字列変換パイプラインへノーレイテンシで自動切り替え。

## 5. 実装および検証方針

1. **`NextPhrasePredictor.kt` の新規作成**:
   - 履歴バイグラムの永続化、頻度ソート、静的連語・助詞辞書、文頭ヒューリスティクスをカプセル化。
2. **`KanaKanjiEngine.kt` / `VoiceInputMethodService.kt` への統合**:
   - 確定時（候補タップ、確定キー、スペース変換確定）に直前の確定フレーズと今回の確定フレーズを記録。
   - 確定直後に `NextPhrasePredictor.predict(lastCommittedSurface)` を呼び出し、候補を `CandidateStripView.setCandidates(...)` に供給。
3. **単体テストの実装**:
   - 履歴学習の動作、コロケーション提示、空入力時のサジェスト、助詞サジェストを検証するJUnitテストスイート。
4. **実機（ARCVM / Phone）デプロイおよび動作確認**:
   - `./deploy.sh` を実行し、確定直後に候補バーにつながり候補が表示され、タップで連続入力できることを検証。
